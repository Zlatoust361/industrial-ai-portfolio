# classical_cv/ — неделя 25: classical CV как альтернатива VLM

Часть [`course/ROADMAP-WEEKS-25-30.md`](../course/ROADMAP-WEEKS-25-30.md)'s
тома 3 — первая неделя, которая НЕ требует GPU/Jetson вовсе. Весь курс
1-24 учит "решать через VLM/детектор"; эта неделя впервые задаёт вопрос
"а нужен ли здесь ИИ вообще" и отвечает на него измеренными числами, не
мнением.

## Что внутри

- `defect_images.py` — генерирует синтетические grayscale-изображения
  "детали" с реальными дефектами через неделю 05's уже протестированный
  `src.synthetic.mask_generation.generate_defect_mask` + реальный
  `config/defects.yaml` (те же `scratch`/`pit`/`crack`, не новый
  словарь дефектов). Новое здесь — только композитинг: дефект реально
  затемняется на фоне (не просто маска), чтобы классический CV имел
  реальный контраст для детекции, не голую бинарную маску.
- `detectors.py` — два классических детектора на настоящем `cv2`, без
  нейросети: Canny + `HoughLinesP` для line-дефектов (scratch/crack),
  threshold + морфология + `findContours` для blob-дефектов (pit), плюс
  NMS-слияние кандидатов по IoU.
- `benchmark.py` — реально измеряет accuracy (AP, precision/recall/F1
  при фиксированном пороге) через уже существующий
  `src.evaluation.detection_metrics` (неделя 07's математика mAP, не
  новая реализация) и латентность (`time.perf_counter()`, настоящие
  миллисекунды на CPU, не оценка).
- `clip_baseline.py` — настоящая попытка CLIP zero-shot (`ok` vs
  `defect`) через неделю 01/02's реальный `src.models.clip.CLIPLoader`/
  `src.models.zero_shot`, тот же чекпоинт
  `openai/clip-vit-base-patch32`, что `captioning/`/`explainability/`/
  `peft/`/`capstone2/`. В этой песочнице — честно упирается в сетевой
  рубеж (нет доступа к `huggingface.co`), репортится как `blocked`, не
  маскируется под победу classical CV по умолчанию.
- `report.py` — собирает сравнение в одном отчёте: реальные числа
  classical CV + либо реальные числа CLIP, либо честный `blocked`.
- `scripts/run_classical_cv_demo.py` — весь деливерабл одной командой.

## Реально измеренные числа (seed=42, 30 positive + 30 negative)

| Метрика | Classical CV (этот прогон) |
|---|---|
| AP (IoU≥0.3) | **0.78** |
| Precision (при score≥0.2) | **0.62** |
| Recall (при score≥0.2) | **0.77** |
| F1 | **0.69** |
| Латентность | **~3.4-4.5 мс/изображение, CPU, без GPU** |
| Ложные срабатывания на 10 чистых изображениях | **0** |

Это реально воспроизводимые числа (`make demo-offline`), не оценка на
глаз — IoU-порог 0.3 (не стандартные 0.5) выбран явно и
задокументирован в `benchmark.py`, потому что classical CV боксы грубые
по конструкции (сегмент Hough с отступом в пару пикселей, не точно
регрессированный прямоугольник YOLO) — честное снижение планки под
реальную природу метода, не подгонка числа под желаемый результат.

CLIP-сторона сравнения в этой песочнице — честно `blocked` (сетевой
рубеж, `httpx2.ProxyError: 403 Forbidden`), не измерена. Рекомендация в
отчёте (`report.py::_recommend`) формулируется из того, что РЕАЛЬНО
измерено за этот прогон, а не из домысленных чисел для недостижимой
стороны.

## Почему IoU-порог 0.3, а не 0.5

Недели 03/06/07/13 (YOLO/open-vocab) используют стандартный IoU=0.5 —
там bbox регрессируется напрямую нейросетью и ожидаемо плотно прилегает
к объекту. `HoughLinesP` и `findContours` дают принципиально более
грубую геометрию: тонкая диагональная линия (scratch/crack) внутри
осевыровненного bbox занимает малую долю его площади, поэтому даже
идеально найденная линия не даст IoU=0.5 с тесным ground truth боксом.
IoU=0.3 — явный, задокументированный компромисс под эту геометрию, не
попытка нарисовать detector лучше, чем он есть (сравни: при IoU=0.5
тот же прогон даёт заметно более низкий AP — честно отражает, что
classical CV локализует грубее, не хуже находит).

## Honesty note

- **Классический CV — полностью реальный код**: настоящий `cv2.Canny`/
  `cv2.HoughLinesP`/`cv2.findContours`, настоящие измеренные
  precision/recall/латентность на CPU этой песочницы. Ничего не
  симулировано.
- **Синтетический, не фотографический датасет**: тестовые изображения —
  процедурно сгенерированные (неделя 05's реальный генератор масок +
  простой darken-композитинг этой недели), не реальные фото деталей с
  камеры. Числа выше корректно отражают поведение детектора на ЭТИХ
  изображениях — перенос на реальные фотографии завода потребует
  повторного измерения, не предполагается автоматически.
- **CLIP-сторона сравнения — честно `blocked`**, не измерена в этом
  первом проходе: эта песочница не имеет доступа к `huggingface.co`.
  `tests/test_clip_baseline.py` проверяет это напрямую через
  `assert_reaches_network_boundary` — тот же паттерн, что
  `captioning/`/`peft/`/`rag/`/`explainability/`.
- **"Molotok dешевле pushki" — вывод про ЭТОТ класс синтетических
  дефектов**, не универсальное правило для всех промышленных кейсов:
  реальные дефекты с низким контрастом, сложной текстурой фона или
  требующие семантического понимания ("этот скол критичен, этот —
  косметический") — именно то, для чего существуют недели 01-02/15,
  не то, что эта неделя пытается заменить.
